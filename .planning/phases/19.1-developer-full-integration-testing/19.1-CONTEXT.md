<decisions>
## Implementation Decisions

### Test Order & Coverage
- **D-01:** Test follows user journey order: init → daily usage (hooks capture + analysis) → scan → apply → status → uninstall. Simulates real user lifecycle from install to teardown.
- **D-02:** Full coverage — all 7 CLI subcommands (init, status, scan, pending, apply-one, dismiss, uninstall), all 6 hooks (user-prompt-submit, permission-request, pre-tool-use, post-tool-use, post-tool-use-failure, stop), both slash commands (/evolve:scan, /evolve:apply), and E2E flows (background analysis → notification → view → apply).

### Test Environment
- **D-03:** Test on this project (harness-evolve) as primary target — dogfooding. Optionally verify on an external project if time permits.
- **D-04:** Start from clean state: uninstall first, then fresh init. This validates the full installation path including version-aware template updates.

### Bug Handling
- **D-05:** Bugs found during testing are fixed inline and testing continues. Each fix gets an atomic commit. No separate bug-fix phase — the goal is to exit this phase with everything working.

### Acceptance Criteria
- **D-06:** Pass/fail checklist — each feature gets a concrete test scenario with expected output. Phase passes when all checklist items are green.
- **D-07:** The checklist should be structured as a executable verification script where possible (CLI commands with expected output), with manual steps only for things requiring Claude Code runtime (slash commands, hook triggers).

### Claude's Discretion
- Specific test scenario details and edge cases to include in the checklist
- Whether to group tests into waves or run sequentially
- How to structure the verification output (markdown report vs inline annotations)

</decisions>
