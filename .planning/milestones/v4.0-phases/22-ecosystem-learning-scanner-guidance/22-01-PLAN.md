    **Template structure (in this exact order):**

    4. **`## Prerequisites`** section (same version check as v3, keep it).

    5. **`## Instructions`** section with 4 steps:
       - Step 1: Gather Context -- run `npx harness-evolve scan-context`, capture the JSON output, parse it. If the command fails, see Error Handling.
       - Step 2: Analyze Configuration -- for each of the 7 analysis areas below, examine the relevant ScanContext fields and check each item in the area's checklist. Produce findings for any issues detected. Aim for 3-8 total findings. Do not exceed 20.
       - Step 3: Store Findings -- format all findings as a JSON array and pipe to `npx harness-evolve store-findings` via stdin: `echo '<json_array>' | npx harness-evolve store-findings`. Check the output for `stored` and `skipped` counts.
       - Step 4: Present Results -- show a human-readable summary. Start with the coverage line "Analyzed N areas, found M finding(s)." Then group by severity (problems first, then suggestions). End with "Run `/evolve:apply` to review and apply fixes."

    6. **`## Analysis Guidance`** section. For each of the 7 areas, use this structure:

       **Area 1: Redundancy** (`scan_redundancy`, default target: `RULE`)
       - What to Check: Same constraint in CLAUDE.md AND .claude/rules/ (duplication). Same setting in user AND project settings.json. Rule file repeating CLAUDE.md content verbatim.
       - Severity Rules: problem if contradictory duplicates (different values). suggestion if benign duplicates (same intent, different wording).
       - Confidence: HIGH if exact text match. MEDIUM if same intent, different wording. LOW if related but not duplicate.
       - Do NOT Flag: Intentional overrides (project settings overriding user settings). CLAUDE.md referencing a rule file (that is cross-referencing, not duplication).

       **Area 2: Missing Mechanization** (`scan_missing_mechanization`, default target: `HOOK`)
       - What to Check: Natural language instructions in CLAUDE.md or rules that describe operations suitable for hooks (e.g., "always run tests before commit", "never push to main"). Validation steps described as "Claude should check" that could be automated.
       - Severity Rules: problem if the operation is critical (data loss, security). suggestion if the operation is a workflow optimization.
       - Confidence: HIGH if the instruction uses imperative language ("must", "always", "never") and describes a hookable lifecycle event. MEDIUM if the instruction is a strong preference. LOW if it is a guideline.
       - Do NOT Flag: Subjective guidance ("prefer X over Y"). Patterns already covered by existing hooks (check hooks_registered). Complex multi-step workflows better suited for skills.

       **Area 3: Stale References** (`scan_stale_reference`, default target: `CLAUDE_MD`)
       - What to Check: @path references in CLAUDE.md pointing to non-existent files. Rule files referencing paths that do not exist in the project. Mentions of tools or commands that are not installed.
       - Severity Rules: problem if the reference is in an instruction users actively follow. suggestion if the reference is in a comment or secondary section.
       - Confidence: HIGH if the referenced path is clearly non-existent in the scan context. MEDIUM if the path might exist outside the scanned scope.
       - Do NOT Flag: npm scoped packages (`@scope/package`). URL user paths (`@user/path`). References to external tools that might be globally installed.

       **Area 4: Conflicts** (`scan_rule_conflict`, default target: `RULE`)
       - What to Check: Contradictory directives (e.g., "use ESM" in one file and "use CommonJS" in another). Conflicting settings between user and project scope without intentional override. Rules that negate each other.
       - Severity Rules: problem if the conflict causes broken behavior (cannot satisfy both). suggestion if the conflict causes confusion but not breakage.
       - Confidence: HIGH if the contradiction is explicit (opposing values for same setting). MEDIUM if the contradiction is semantic (different wording, conflicting intent). LOW if potentially intentional tension.
       - Do NOT Flag: Intentional scope overrides (project overrides user). Complementary rules that appear contradictory but cover different scopes.

       **Area 5: Structure Issues** (`scan_structure_issue`, default target: `RULE`)
       - What to Check: Empty rule files (0 bytes or only whitespace). Oversized rule files (>200 lines -- may need splitting). Rule files without headings (poor organization). Rules in subdirectories without path-scoping frontmatter. CLAUDE.md exceeding 500 lines.
       - Severity Rules: problem if empty rule file (provides no value, adds noise). suggestion for oversized files or poor organization.
       - Confidence: HIGH if file is empty or missing content entirely. MEDIUM if file is oversized. LOW if organization could be improved.
       - Do NOT Flag: Small rule files (<10 lines) that are focused and complete. CLAUDE.md files under 200 lines. Subdirectory rules that are intentionally broad.

       **Area 6: Hooks Quality** (`scan_hooks_redundancy`, default target: `SETTINGS`)
       - What to Check: Duplicate hooks (same event + same command registered twice). Overlapping hooks (different commands doing the same check on the same event). Hooks registered in settings but pointing to non-existent scripts. Hooks without error handling (missing `|| true` for non-critical hooks).
       - Severity Rules: problem if hook script does not exist (will fail at runtime). problem if exact duplicate (wastes execution time). suggestion if hooks overlap.
       - Confidence: HIGH if script path is clearly non-existent. HIGH if exact command match. MEDIUM if commands appear to overlap.
       - Do NOT Flag: Multiple hooks on the same event doing different things (that is valid composition). harness-evolve's own hooks (they are managed by the tool).

       **Area 7: Commands Quality** (`scan_command_convention`, default target: `SKILL`)
       - What to Check: Command files missing YAML frontmatter (name, description). Empty command files. Commands without `description` field (poor discoverability). Commands with overly generic names. Commands referencing non-existent tools or paths.
       - Severity Rules: problem if command file is empty (non-functional). suggestion for missing frontmatter or poor naming.
       - Confidence: HIGH if file is empty. MEDIUM if frontmatter is missing. LOW if naming could be improved.
       - Do NOT Flag: Commands that intentionally skip frontmatter for specific technical reasons. Short commands (<5 lines) that are clear without description.

    7. **`## Severity Classification`** section. A decision matrix table:
       | Condition | severity | confidence |
       |-----------|----------|------------|
       | Config is broken or contradictory | problem | HIGH |
       | Config works but has redundancy or duplication | suggestion | MEDIUM |
       | Config could benefit from mechanization | suggestion | MEDIUM |
       | Style or convention improvement | suggestion | LOW |
       | Referenced file does not exist | problem | HIGH |
       | Referenced file might not exist | suggestion | MEDIUM |

       Include note: "When in doubt, prefer suggestion over problem, and MEDIUM over HIGH. Conservative classification reduces false positives."

    8. **`## Output Format`** section. Define the exact JSON structure with a complete example:
       ```json
       {
         "id": "scan-redundancy-abc123",
         "target": "RULE",
         "confidence": "HIGH",
         "pattern_type": "scan_redundancy",
         "title": "Duplicate constraint in CLAUDE.md and rules/coding.md",
         "description": "The instruction 'always use TypeScript strict mode' appears in both CLAUDE.md (line 12) and .claude/rules/coding.md (line 5). This creates maintenance burden -- update one and the other becomes stale.",
         "evidence": {
           "count": 1,
           "examples": ["CLAUDE.md line 12: 'Use TypeScript strict mode'", "rules/coding.md line 5: 'Always enable strict mode in TypeScript'"]
         },
         "suggested_action": "Remove the constraint from CLAUDE.md and keep it in .claude/rules/coding.md where it is more specific and maintainable.",
         "severity": "suggestion"
       }
       ```
       List all valid values:
       - `pattern_type`: scan_redundancy, scan_missing_mechanization, scan_stale_reference, scan_rule_conflict, scan_structure_issue, scan_hooks_redundancy, scan_command_convention
       - `target`: HOOK, SKILL, RULE, CLAUDE_MD, MEMORY, SETTINGS
       - `confidence`: HIGH, MEDIUM, LOW
       - `severity`: problem, suggestion
       - `evidence.examples`: maximum 3 strings
       - `id` format: `scan-{area}-{short-hash}` (e.g., scan-redundancy-a1b2c3). Use any short unique string for the hash.

    9. **`## Boundary Conditions (What NOT to Flag)`** section. Global exclusions:
       - npm scoped packages (`@scope/package`) are NOT stale references
       - URL user paths (`/@user/path`) are NOT stale references
       - Empty `.claude/` directory is normal for new projects
       - Global-only configuration (no project-level config) is a valid setup
       - harness-evolve's own hooks are NOT redundant
       - Intentional scope overrides (project overriding user) are NOT conflicts
       - Do not produce more than 20 findings total
       - Aim for 3-8 findings on a typical config. Zero findings is valid for clean configs.

    10. **`## Error Handling`** section:
        - scan-context command fails: show error, suggest `harness-evolve status`
        - store-findings reports skipped > 0: show which findings failed validation and why
        - scan-context returns empty/minimal context: report "No configuration files found" and suggest running `harness-evolve init`

    11. **`## Edge Cases`** section:
        - No `.claude/` directory: report minimal findings, this is normal for new projects
        - Very large configs (50+ rules files): focus on highest-severity findings, stay within 20 max
        - No internet required: scan runs entirely locally

    12. **`## Notes`** section:
        - Findings stored via store-findings are available in `/evolve:apply`
        - Re-running scan replaces previous scan results
        - Each analysis area maps to a `pattern_type` value for routing and tracking

    **Language instruction:** Include in the Output Format section: "Default to English for all output. If the user has explicitly requested a different language for this session, use that language for the human-readable summary only. JSON findings MUST always use English."
