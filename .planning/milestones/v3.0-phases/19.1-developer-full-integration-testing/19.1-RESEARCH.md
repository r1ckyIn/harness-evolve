## Summary

This phase is a developer-driven manual integration test of the complete harness-evolve v3.0 feature set. The system under test is a CLI tool with 7 subcommands, 6 Claude Code hooks, and 2 slash commands. The testing approach must accommodate two distinct runtime environments: (1) shell-level CLI commands that can be scripted and verified programmatically, and (2) Claude Code runtime features (hooks, slash commands, notifications) that require a live Claude Code session.

The current environment state is favorable for a clean-state test: no harness-evolve hooks are registered in `~/.claude/settings.json`, no slash commands exist at `~/.claude/commands/evolve/`, but residual data exists at `~/.harness-evolve/` from prior usage. The existing automated test suite (708 tests, all passing) validates unit and integration logic; this phase validates the real-world user experience end-to-end.

**Primary recommendation:** Structure as a two-part test plan: (1) a shell-scriptable verification script for all CLI commands with expected output assertions, and (2) a manual verification checklist for Claude Code runtime features. Fix the known DTS build error (missing `severity` field in onboarding classifiers) as a pre-test cleanup step.

## Architecture Patterns

### Test Boundary Classification

Every feature falls into one of two testability categories:

| Category | Features | How to Test | Automatable? |
|----------|----------|-------------|--------------|
| **Shell-scriptable** | All 7 CLI subcommands, dist/ file existence, settings.json mutations, data directory operations | Run CLI commands, check exit codes, parse JSON stdout, verify file system state | YES -- bash script |
| **Claude Code runtime** | 6 hooks (stdin JSON -> behavior), 2 slash commands (/evolve:scan, /evolve:apply), notification injection (stdout write during hook) | Must run inside a live Claude Code session where hooks are triggered by real events | NO -- manual checklist |

### Recommended Test Structure: Waves

Group tests into sequential waves following the user journey (D-01):

```
Wave 0: Pre-flight (clean state + build verification)
  ├── Uninstall any existing installation
  ├── Fix DTS build error (tech debt cleanup)
  ├── Rebuild: npm run build succeeds cleanly
  └── Verify test suite: npm test passes

Wave 1: Init & Installation (CLI scriptable)
  ├── harness-evolve init --yes
  ├── Verify 6 hook events in settings.json
  ├── Verify slash commands at ~/.claude/commands/evolve/
  ├── Verify template-version comments in installed .md files
  └── Verify deep scan runs during init

Wave 2: CLI Subcommands (CLI scriptable)
  ├── harness-evolve status (interaction count, hooks registered)
  ├── harness-evolve scan (JSON output with problems/suggestions)
  ├── harness-evolve pending (JSON output with pending array)
  ├── harness-evolve apply-one <id> (apply a scan recommendation)
  ├── harness-evolve dismiss <id> (dismiss a recommendation)
  └── harness-evolve status (verify applied/dismissed reflected)

Wave 3: Hooks & E2E (Manual in Claude Code session)
  ├── Trigger UserPromptSubmit (send a prompt, check log capture)
  ├── Trigger tool hooks (use Bash/Read/Write, check tool logs)
  ├── Trigger PermissionRequest (if any permission prompts appear)
  ├── Trigger Stop hook (end a response, check analysis trigger)
  ├── Verify notification injection (after analysis, next prompt shows notification)
  ├── Run /evolve:scan slash command
  └── Run /evolve:apply slash command

Wave 4: Uninstall & Teardown (CLI scriptable)
  ├── harness-evolve uninstall --yes
  ├── Verify hooks removed from settings.json
  ├── Verify slash commands removed from ~/.claude/commands/evolve/
  ├── harness-evolve uninstall --purge --yes
  └── Verify ~/.harness-evolve/ deleted
```

### Anti-Patterns to Avoid
- **Testing against mocked state:** This phase tests REAL file system, REAL settings.json, REAL Claude Code runtime. No mocks.
- **Skipping cleanup verification:** The uninstall path is as important as the install path. Verify zero residual state.
- **Testing only happy path:** Include error cases: what happens when you `apply-one` a nonexistent ID? What does `scan` output when config is clean?

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON output verification | Custom JSON diff tool | `jq` CLI + shell string matching | Standard, reliable, already available |
| File existence checks | Custom Node.js scripts | `test -f` / `ls` shell commands | Simpler, no compilation needed |
| Settings.json parsing | Node.js parser | `python3 -c "import json..."` or `jq` | Quick inline checks without build |
| Hook stdin simulation | Custom stdin piping | `echo '{"json":"payload"}' \| node dist/hooks/X.js` | Direct stdin piping to hook binaries |

## Common Pitfalls

### Pitfall 1: npx Cache Stale Binary
**What goes wrong:** `npx harness-evolve` may resolve to a cached older version from a previous `npx` invocation, not the freshly built `dist/cli.js`.
**Why it happens:** npx caches resolved packages in `.npm/_npx/` and may not pick up local changes.
**How to avoid:** Use `node dist/cli.js` for local testing instead of `npx harness-evolve`. Or run `npm link` first to create a proper global symlink.
**Warning signs:** Version mismatch between `node dist/cli.js --version` and `npx harness-evolve --version`.

### Pitfall 2: Residual Data Directory Pollutes Tests
**What goes wrong:** `~/.harness-evolve/` contains old counter.json, config.json, and analysis results from prior runs. Fresh init does NOT purge this directory -- it only registers hooks and installs commands.
**Why it happens:** Init is designed to be non-destructive (preserve user data). But for testing, stale data means `status` shows old counts and `pending` may return stale recommendations.
**How to avoid:** Wave 0 must explicitly `rm -rf ~/.harness-evolve/` before fresh init, or use `harness-evolve uninstall --purge --yes` first.
**Warning signs:** `status` showing non-zero interaction counts immediately after init.

### Pitfall 3: DTS Build Error Masking Real Type Errors
**What goes wrong:** The known DTS error in onboarding classifiers (missing `severity` field) causes `npm run build` to exit non-zero even though JS bundles succeed. If new type errors are introduced, they get lost in the noise.
**Why it happens:** tsup runs ESM build (succeeds) then DTS build (fails). Exit code is non-zero.
**How to avoid:** Fix the DTS error first (add `severity: 'suggestion'` to 4 onboarding recommendations). Then `npm run build` becomes a clean gate.
**Warning signs:** `npm run build` exits non-zero.

### Pitfall 4: Hook Testing Requires Correct JSON Schema on stdin
**What goes wrong:** Piping malformed JSON or wrong schema to hook binaries results in silent exit (hooks swallow all errors by design).
**Why it happens:** Hooks use Zod schemas to validate stdin JSON. Invalid input is caught and ignored.
**How to avoid:** Use exact JSON shapes matching the Zod schemas in `src/schemas/hook-input.ts`. Reference existing test fixtures.
**Warning signs:** Hook runs successfully but produces no log entries.

### Pitfall 5: Slash Command Testing Requires Live Claude Code
**What goes wrong:** Attempting to test `/evolve:scan` and `/evolve:apply` from a regular shell fails because these are Claude Code slash commands that inject context into a Claude session.
**Why it happens:** Slash commands are `.md` files parsed by Claude Code's command system, not executable scripts.
**How to avoid:** Wave 3 (manual testing) must be done inside a Claude Code session. The CLI equivalents (`harness-evolve scan`, `harness-evolve pending`, `harness-evolve apply-one`) can be verified in shell.
**Warning signs:** Trying to execute `.md` files directly.

### Pitfall 6: Stop Hook Analysis Threshold
**What goes wrong:** The Stop hook only triggers analysis when `counter.total >= config.analysis.threshold` (default: 50 interactions) and cooldown has elapsed. In testing, the counter won't naturally reach 50.
**Why it happens:** The threshold prevents analysis on every response.
**How to avoid:** Either (a) manually set counter.json total to a high value before testing, or (b) lower the threshold in config.json, or (c) call `checkAndTriggerAnalysis()` directly via a test script.
**Warning signs:** Stop hook runs but analysis never triggers.
